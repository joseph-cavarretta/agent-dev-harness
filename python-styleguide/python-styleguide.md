# Python Style Guide

Standards for Python code. These apply to every change, whether written by a human, generated by an AI tool, or a mix.

> **Maintaining this document:** Keep it direct, concise, and actionable. Do not add filler, over-explain concepts, or pad sections for completeness. If a rule can be stated in one sentence, use one sentence. If a section stops being relevant, delete it. This document should be as lean as the code it governs.

---

## Why These Guidelines Exist

AI coding tools are now part of the development workflow. They increase the speed at which code is produced, but speed without standards produces slop. AI-generated code trends toward verbose, loosely-typed, convention-ignoring output unless it is held to explicit rules.

Without strict guardrails:
- Env vars get accessed directly via `os.getenv` instead of typed config
- Functions grow to thousands of lines because the tool doesn't know when to stop
- Business logic lands in I/O and orchestration layers because the tool doesn't understand the architecture
- Untyped dicts proliferate because the tool defaults to the path of least resistance
- Tests mock everything instead of using clean dependency boundaries
- Every file gets a module-level docstring and every function gets a paragraph that restates the code
- Existing utilities and patterns get reimplemented because the tool doesn't know what's already there

These guidelines are not aspirational. They are the minimum standard for code entering a repo.

**The bar is: if code doesn't meet these guidelines, it doesn't merge.** Every line in a change should be code you understand and would stand behind. AI tools are pointed at this document, but reviewers are the last line of defense.

---

## How This Document Is Enforced

This guide covers only what needs judgment. Anything a linter can decide lives in `ruff-base.toml` and `docstring_length.py` alongside this file, and is **not** restated here — see [Enforced Mechanically](#enforced-mechanically) at the end for what those cover.

The split matters: a linter rule is free and always obeyed, a paragraph here costs tokens on every read and is obeyed most of the time. If you find yourself wanting to add a rule below, first check whether it can be expressed as a check instead. Prose is the fallback, not the default.

## 1. Module Size and Structure

**No multi-thousand-line files.** If a module exceeds ~300-500 lines, break it into logical components.

Large functions are a code smell. If a function exceeds ~50 lines, extract sub-functions. If a module is growing because it handles multiple responsibilities, split it by concern.

```
# Bad: one 800-line module doing parsing, validation, transformation, and persistence
order_processor.py -> process_orders() handles everything

# Good: each concern in its own module
parsing.py         -> parse_order(), extract_line_items()
validation.py      -> validate_schema(), check_required_fields()
transform.py       -> normalize_fields(), apply_discounts()
persistence.py     -> save_order(), archive_order()
```

Linters cannot count lines meaningfully, so these limits are enforced by proxy — statement count, branch count, and cyclomatic complexity. Code can pass those checks and still be too long. Use judgment.

## 2. Comments and Docstrings

**Every function gets a docstring.** Scale detail to complexity. Do not restate the function name and signature in paragraph form.

**Write docstrings as prose, not sections.** No `Args:` / `Returns:` / `Raises:` blocks. Type annotations already state the types, and parameter names already state the names — a section block that repeats both adds length without adding information. Describe what the function does, and what a caller needs to know that isn't visible in the signature.

```python
# BAD -- section blocks restating the signature
def get_order(self, order_id: str) -> Order:
    """Get an order by its ID.

    Args:
        order_id: The ID of the order to get.

    Returns:
        An object containing the order data.
    """
    return self._get(f"/orders/{order_id}")

# GOOD -- simple one-liner for a simple function
def get_order(self, order_id: str) -> Order:
    """Fetch a single order by ID."""
    return self._get(f"/orders/{order_id}")

# GOOD -- prose for complex behavior: says what the signature cannot
def archive_order(self, order_id: str, reason: str) -> ArchivedOrder:
    """Move an order to the archive store, then soft-delete the live record.

    The archive key is deterministic based on order_id and the original
    created-at date, so re-archiving the same order overwrites rather than
    duplicating. Raises OrderNotFoundError if the live record is already gone.
    """
```

**Rules:**
- No module-level docstrings unless the module's purpose is genuinely non-obvious from its name and contents
- No inline comments that restate the next line
- Do add comments when the *why* is not obvious — business rules, non-obvious constraints, workarounds, and anything that will look like a mistake to the next reader
- Document what a caller would get wrong: units, ownership, mutation, ordering guarantees, idempotency, whether a failure is retryable
- `TODO:` comments carry a ticket reference and what needs doing, never a person's name
- Docstring and comment lines wrap at the same 88 characters as code. The formatter does not reflow prose, so this is a lint check (`W505`), not something the formatter fixes for you

**When a long line is genuinely unavoidable.** A line whose overflow is one unbreakable token — a URL, a filesystem path, a long identifier — is exempt automatically. Put it on its own line and nothing complains; no directive needed. That covers most real cases.

For anything else, `# noqa: W505` goes **after the closing `"""`**, where it suppresses the whole docstring:

```python
def build_query(spec: QuerySpec) -> str:
    """Render the BM25 query.

    Mirrors the field weights in the OpenSearch pipeline definition exactly, because a mismatch scores silently wrong rather than erroring.
    """  # noqa: W505
```

A `noqa` placed *inside* the docstring does nothing at all — it becomes part of the string. On the `def` line it also does nothing. Both fail silently, which is worse than not trying, so this is the one placement to remember.

**Cap the number of lines, not just their width.** A width limit stops a docstring from hiding its bulk on one long line. It does nothing about forty wrapped ones. Both caps below count physical lines from the opening `"""` to the closing `"""` — the vertical space a reviewer scrolls past:

| | soft | hard |
|---|---|---|
| Function and class docstrings | 8 | 20 |
| Module docstrings | 10 | 25 |
| Module docstrings in `scripts/` | — | 60 |

The soft cap is a norm, not a failure. Crossing it is the prompt to ask whether the docstring is explaining or restating. The hard cap fails. Anything that genuinely needs more than the hard cap is not function documentation — it belongs in a module docstring, a wiki page, or a comment sitting next to the line that actually needs explaining.

**The sharpest signal is relative: a docstring longer than the function body it documents is almost always a restatement.** Nothing that short needs that much explaining. Treat it as a failure whatever the absolute count says.

The reason for all of this is reviewer cognitive load. An LLM will write four paragraphs where one sentence carries the information, and every one of those lines is something a human has to read past to reach the code. Redundant prose does not sit inertly next to the code — it competes with it for attention, and it goes stale while looking authoritative.

**`scripts/` and `.local/` are not linted at all.** Both are loose by design. `scripts/` holds one-off operational tools where the module docstring *is* the usage text someone reads before running it, so usage blocks, argument lists, and sample invocations are supposed to be long. `.local/` is scratch work that was never meant to meet production rules. Neither directory is subject to the caps above, the width limit, or any other lint rule.

```toml
extend-exclude = [".local"]         # scratch: not linted, not formatted

[lint]
exclude = ["**/scripts/**"]         # loose rules, but still formatted
```

The two settings are not the same. A top-level `exclude` skips linting *and* formatting; `[lint].exclude` skips linting only. `scripts/` still gets formatted, because formatting carries no judgment and keeps diffs readable. `.local/` is left alone completely.

The two settings also match paths differently. A top-level `exclude` matches a bare
directory name at any depth; `[lint].exclude` does not, so it needs the full
`**/scripts/**` glob or it silently misses nested directories.

Ruff does not skip dot-directories on its own. `.local/` is exempt only because it is named here — it also gets skipped when gitignored, which is not something to depend on.

## 3. Type Annotations

**Everything is annotated and type-checked in strict mode.** Every function signature — parameters and return — carries annotations, including private helpers and tests. `__init__` returns `-> None`. Do not annotate `self` or `cls`.

Types are the primary interface documentation, which is why docstrings don't repeat them. That only works if they're complete and accurate.

**Use the modern spellings. `typing` is now mostly a legacy shim.** Three separate substitutions, and the middle one is the one that gets missed:

- **Builtin generics** (PEP 585) — `list[str]`, `dict[str, int]`, `tuple[int, ...]`, `set[str]`, `type[Order]`. Never `List`, `Dict`, `Tuple`, `Set`, or `Type` from `typing`.
- **Abstract types come from `collections.abc`**, not `typing` — `Sequence`, `Mapping`, `Iterable`, `Iterator`, `Callable`, `Awaitable`, `Generator`. The `typing` spellings still import and still work, so nothing fails at runtime to tell you they're wrong.
- **Union operators** (PEP 604) — `X | Y` and `X | None`. Never `Union[...]` or `Optional[...]`.

```python
# WRONG -- legacy typing spellings
from typing import Dict, List, Optional, Sequence, Union

def load(ids: List[str], cfg: Optional[Dict[str, Union[int, str]]] = None) -> Sequence[Order]: ...

# RIGHT -- builtins, collections.abc, and | unions
from collections.abc import Sequence

def load(ids: Sequence[str], cfg: dict[str, int | str] | None = None) -> list[Order]: ...
```

What still legitimately comes from `typing`: `Any`, `Literal`, `Protocol`, `TypeAlias`, `TypeVar`, `ParamSpec`, `Final`, `ClassVar`, `Self`, `cast`, `overload`, `Annotated`, and `TYPE_CHECKING`.

Repos targeting below Python 3.10 are exempt and pin `target-version` to say so. `from __future__ import annotations` permits the modern spellings in annotations there, but not where an annotation is evaluated at runtime — which is what Pydantic does to build a model, so it is not a general escape hatch.

**Accept the widest type you can use; return the narrowest type you have.**

```python
# GOOD -- caller can pass a list, tuple, or any sequence; gets a concrete dict back
def count_by_status(orders: Sequence[Order]) -> dict[str, int]: ...

# BAD -- forces the caller to materialize a list; hides the concrete return
def count_by_status(orders: list[Order]) -> Mapping[str, int]: ...
```

Take `Sequence`, `Mapping`, and `Iterable` (from `collections.abc`) as parameters; return concrete `list`, `dict`, and `set`. Take `Iterable` only when you consume it once — if you iterate twice, take `Sequence`. For a set parameter the abstract type is `collections.abc.Set`, which reads confusingly next to builtin `set`; alias it to `AbstractSet` where the difference matters.

**`Any` requires a comment explaining why.** It disables checking for everything it touches. Where the value is genuinely unknown but you intend to narrow it, use `object` — the type checker will then force the narrowing.

**Name complex types.** If a type appears more than once, or is a nested generic, give it a `TypeAlias`. Module-local aliases get a leading underscore.

```python
_ScoredChunks: TypeAlias = list[tuple[Chunk, float]]
```

**Use `Protocol` at dependency boundaries.** Anything with more than one real implementation, or that needs a test double, gets a Protocol rather than an ABC. Reserve ABCs for genuine shared implementation, and never more than one level deep.

**Never use implicit optional.** `def f(x: str = None)` is wrong; write `x: str | None = None`. Use `X | None`, not `Optional[X]`.

**`if TYPE_CHECKING:` is for type-level cycles only.** A cycle in runtime code means the layering is wrong — fix the structure. Do not use `TYPE_CHECKING` to make a bad dependency arrow pass the linter.

**`# type: ignore` names its error code and its reason.** A bare ignore is a silent hole.

```python
result = client.fetch(key)  # type: ignore[no-any-return]  # vendor stub returns Any
```

## 4. Environment Variables and Config Propagation

**All environment variables flow through a typed Pydantic `BaseSettings` model.** Never `os.environ`, `os.getenv`, or any direct env var access.

```python
# WRONG -- untyped, unvalidated, scattered
enabled = os.getenv("IS_ENABLED", "false").lower() == "true"
url = os.environ["API_URL"]

# RIGHT -- typed, validated, single source of truth
class AppConfig(BaseSettings):
    model_config = SettingsConfigDict(extra="forbid")

    notifications_enabled: bool = Field(
        default=False,
        description="Send notifications when an order is archived.",
    )
    api_url: str = Field(description="Base URL for the orders API.")
```

`case_sensitive=False` is the default, so `NOTIFICATIONS_ENABLED` already maps to
`notifications_enabled` without help. Reach for `validation_alias` only when an existing
env var differs from the field name by more than casing:

```python
    backend_url: str = Field(validation_alias="CORE_BACKEND_URL")
```

Give every field a `description`. It is the only documentation a setting gets, and it
shows up wherever the config is introspected.

**Config propagation:** `get_settings()` is called **once at the entry point** (app lifespan, CLI main, worker startup, script). Everything below the entry point receives the config object as an explicit, required constructor parameter.

```python
# WRONG -- lib reaches for global singleton
class Processor:
    def __init__(self) -> None:
        self._config = get_settings()  # hidden dependency

# WRONG -- optional config with fallback
class Writer:
    def __init__(self, config: AppConfig | None = None) -> None:
        self._config = config or get_settings()  # unclear who owns config

# RIGHT -- config is required, passed by caller
class Writer:
    def __init__(self, config: AppConfig) -> None:
        self._config = config
```

Do not create derived config models that duplicate fields from the settings class. One config class, one source of defaults. If a component only needs a subset of fields, accept the full config and use what it needs. Constructor defaults must not restate a config field's default — config owns the default.

**Why:** env vars are validated at startup rather than at first use, types are checked automatically, all config is visible in one place, tests override with `config.model_copy(update={...})`, and an explicit parameter makes the dependency obvious.

**No other mutable global state either.** Module-level mutable values are the same problem wearing a different hat: they make import order matter, they leak between tests, and they make behavior depend on what ran earlier. Module-level *constants* are fine and encouraged. Where a process-lifetime cache is genuinely needed (a connection pool, a compiled model), keep it module-private, reach it through a function, and say in a comment why it is safe to share.

## 5. Data Models

**All structured data uses Pydantic `BaseModel`.** No `TypedDict`, no raw `dict[str, Any]` for structured data, no mutable dataclasses.

```python
class OrderRequest(BaseModel):
    model_config = ConfigDict(strict=True, extra="forbid", frozen=True)
    source: Literal["web", "api"]
    line_items: list[LineItem]
    customer_id: str
```

Baseline defaults:
- `strict=True` — no silent type coercion
- `extra="forbid"` — reject unknown fields, which catches typos and upstream schema drift
- `frozen=True` — for anything passed between stages or used as a value object

Opt out of `frozen` only when a model is genuinely meant to be mutated: accumulators, builders, records populated incrementally.

**When to create a model:** if data is passed between functions, returned from a function, or received from an external source, it gets a model. A `dict[str, Any]` accessed by string keys is a model waiting to be defined.

Validate at the boundary. Parse external input into a model once, at the edge, and pass the model inward — never pass raw payloads through several layers and validate deep in the stack.

## 6. Imports

**Absolute imports only. Never relative.** `from services.orders import parsing`, never `from . import parsing` or `from ..models import Order`. Relative imports break when a module moves and make it impossible to tell where a name comes from.

Importing symbols is fine — `from pydantic import BaseModel` is correct and expected. Import a module instead when the symbol name alone would be ambiguous at the call site (`schemas.Order` reads better than a bare `Order` when three modules define one).

**Alias anything that shadows.** If an imported name collides with a builtin, a common parameter name, or another import, alias it rather than letting the shadow stand.

**Imports go at the top of the file.** Two exceptions: a genuinely optional heavy dependency loaded behind a feature flag, and `if TYPE_CHECKING:` blocks. Never import inside a function to break a cycle — that hides a structural problem instead of fixing it.

**`__init__.py` is a public surface, not a dumping ground.** Either keep it empty, or re-export deliberately with an explicit `__all__`. An `__init__.py` that imports everything below it creates import cycles and makes every submodule load whenever anything loads.

Ordering and grouping are handled by the formatter — see [Enforced Mechanically](#enforced-mechanically).

## 7. Naming

Case conventions are linter-enforced. What needs judgment:

**Names say what the thing is, not what type it is.** The annotation states the type; repeating it in the name means updating two places.

```python
# BAD
order_dict: dict[str, Order]
id_list: list[str]
config_obj: AppConfig

# GOOD
orders_by_id: dict[str, Order]
customer_ids: list[str]
config: AppConfig
```

**Ban placeholder names as the whole name:** `data`, `info`, `obj`, `item`, `temp`, `result`, `helper`, `handler`, `manager`, `util`, `process`. Each is a prompt to think about what the thing actually is. As a qualified part of a longer name they're fine — `result_count` is clear, `result` is not.

**Single letters** only for loop counters, `e` in an `except` clause, and established mathematical notation with the source cited in a comment.

**Booleans read as assertions:** `is_enabled`, `has_attachments`, `should_retry`. A boolean named `status` or `flag` tells the reader nothing about which way is true.

**Module-private gets one leading underscore.** Never use double-underscore name mangling — it defeats testing and buys almost nothing.

## 8. Project Structure

**Keep business logic separate from infrastructure and orchestration.** Business logic
should be testable without spinning up infra, and infra concerns (retry, caching, state,
I/O) should stay out of business logic.

Two rules carry most of the weight:

1. **Pure logic knows nothing about its callers or its I/O.** No framework imports, no
   network/disk/database calls inside functions that compute or decide. Those functions
   take data in and return data out.
2. **Imports point one direction — toward pure logic.** Everything above depends on what
   sits below it; nothing below knows anything above it exists.

### The default layout

Use this tree. It is the default so that layout stops being a decision, and so two
projects written a year apart look the same.

```
src/<package>/
  __init__.py
  models.py       data contracts (Pydantic). Imports nothing from the package.
  config.py       BaseSettings. Imports models.
  errors.py       exception hierarchy. Imports nothing.
  core/           pure logic. No I/O, no framework, no clock, no randomness.
  infra/          everything impure: clients, storage, queues, framework glue.
  app/            orchestration. One module per use case.
  entrypoints/    how the process starts: CLI main, ASGI app, worker, flow.
tests/            mirrors the package tree
scripts/          one-off operational tools. Loose — not linted (see §2).
```

Arrows run one way:

```
entrypoints/ -> app/ -> infra/ -> core/ -> models.py, config.py, errors.py
```

**The line that matters is `infra/`.** Above it you may touch the world. Below it you
may not.

- `core/` is the part worth protecting. A function here takes data and returns data. If
  it needs the time, the network, a database, or a random number, that arrives as an
  argument. This is what makes it testable without infrastructure (§12).
- `infra/` holds everything that exists because the outside world does — HTTP clients,
  database repositories, storage, queue producers — **and** everything that exists
  because a framework demands it: a Prefect `@task`, a Celery task, a FastAPI
  dependency, a Click decorator. None of that code has domain meaning. It wraps
  something that does.
- `app/` sequences `infra/` and `core/` into one module per use case. It decides order,
  not policy.
- `entrypoints/` is wiring only: read config once (§4), construct what is needed, hand
  off to `app/`. No logic lives here.

Subdivide `infra/` when it earns it rather than up front — `infra/clients/`,
`infra/storage/`, `infra/tasks/`.

### Permitted variations

These are the deviations that need no justification:

- **A library** is `models.py`, `errors.py`, and `core/`. No `app/`, no `entrypoints/`.
  If it grows I/O, that goes in `infra/`.
- **A CLI or small service** may fold `app/` into `entrypoints/` while there is exactly
  one use case. Split it the moment there are two.
- **A framework-shaped project** keeps the framework's names where the framework
  requires them. A Prefect service reads `libs/ -> core/`, `tasks/ -> infra/`,
  `flows/ -> app/`. Different words, identical arrows.
- **A single-file tool** is a single file in `scripts/`. Do not build a package around
  eighty lines.

Anything beyond these is a deviation, and a deviation gets one sentence in the repo's
own styleguide saying what it is and why.

### Across units

A shared utility layer (e.g. `shared/`) may be imported by anything, but must never
import from a specific feature or service.

Peers at the same level do not import each other either. Two services, two features, two
plugins — if one needs something from the other, that something belongs in the shared
layer. A direct peer import couples two things that were meant to be replaceable
independently.

If you find yourself adding a lazy import to dodge a circular dependency, the layering is
wrong — fix the structure.

## 9. Error Handling

**Every distinct failure mode gets a named exception class, and every name ends in `Error`.** Each package defines one base error and inherits from it, so callers can catch the package's failures as a group.

```python
class OrderServiceError(Exception):
    """Base for every error raised by this package."""

# Transient -- worth retrying; same call may succeed later
class UpstreamServiceError(OrderServiceError): ...   # 5xx, timeout, connection reset
class StorageError(OrderServiceError): ...           # transient backend failure

# Permanent -- same input will produce the same failure
class OrderValidationError(OrderServiceError): ...   # input cannot be parsed
class OrderNotFoundError(OrderServiceError): ...     # nothing to act on
```

The retryable/permanent split is the distinction that matters most: it decides whether the retry layer should act or give up. Make it visible in the class hierarchy or in the docstring, not just in the caller's head.

**Rules:**
- Never `assert` in production code. Assertions are stripped under `-O`, so an assert is a check that may not run. If prior logic guarantees the condition, just use it; if it needs a runtime check, raise. Asserts in tests are fine.
- Never a bare `except:`. Catch `Exception` only to re-raise, or at a top-level isolation point that logs and keeps the process alive.
- Keep the `try` block down to the statement that can actually fail. A wide `try` swallows errors you didn't intend to handle.
- Chain with `raise NewError(...) from err`. Dropping the cause discards the traceback that explains the failure.
- Avoid catching and swallowing silently (`except Exception: return []`). Occasionally correct for best-effort work that must not block the main flow — but it must be logged and the reason documented.
- Never hand-roll retry loops with `time.sleep()`. Use the framework's retry facility or `tenacity`, and scope it to the transient exceptions only.
- Let transient exceptions propagate to the retry layer; don't retry deep inside business logic.
- Raise permanent errors immediately so they surface instead of being retried pointlessly.

## 10. Logging

**One logger per module:** `logger = logging.getLogger(__name__)`. Never the root logger. Never `print()` except as a CLI's actual output.

**Pass pattern strings, not f-strings.** `logger.info("indexed %s chunks for %s", count, doc_id)` defers formatting until the record is emitted and keeps messages groupable by shape. An f-string produces a unique string per call, which makes aggregation and alerting useless.

**Log where you have context, once.** Log-and-raise duplicates the same failure at every level. Either handle it and log, or raise and let the boundary log it.

**Never log secrets, credentials, tokens, connection strings, or customer-identifying data.** This includes exception payloads and request bodies, which routinely carry both.

Choose the level deliberately: `debug` for tracing, `info` for lifecycle and outcomes, `warning` for degraded-but-working, `error` for work that failed and needs attention. Everything at `info` is the same as nothing at `info`.

## 11. Concurrency

**Pick one model per module.** Don't mix sync and async in the same layer. A sync function that spins up an event loop to call one async client is a sign the boundary is in the wrong place.

**Never call blocking I/O inside `async def`.** No `requests`, no blocking DB driver, no `time.sleep`, no large file read. Use an async client, or hand it to `asyncio.to_thread`. One blocking call stalls every task on the loop.

**Bound concurrency explicitly.** Pool sizes, semaphore limits, and batch sizes come from config — never an unbounded `gather` over an input list whose length you don't control.

**Don't share mutable state between workers.** Pass data in and results out. Where shared state is unavoidable, the lock and the invariant it protects go in a comment together.

## 12. Testing

**Tests must not require external infrastructure.** No port-forwarding, no live databases, no real cloud storage.

- **Config via fixture:** use a shared `conftest.py` fixture and override with `config.model_copy(update={...})` — never `os.environ` in tests.
- **Prefer stubs over mocks:** inject lightweight stub classes rather than patching internals with `unittest.mock.patch`. Reserve mocks for external library calls that can't be injected. A test that patches five internals is testing the implementation, not the behavior.
- **Test logic directly:** most tests target pure business logic. Reserve heavier tests for adapters (I/O behavior) and end-to-end wiring.
- **Test behavior, not implementation.** Assert on what the function returns or the effect it has, not on which private helpers it called.
- Tests are annotated and linted like everything else, and are exempt only from the docstring rule.

```python
# conftest.py
@pytest.fixture()
def config() -> AppConfig:
    return AppConfig(api_url="http://api/", storage_root="test-store")

# test file
def test_notifications_skipped_when_disabled(config: AppConfig) -> None:
    cfg = config.model_copy(update={"notifications_enabled": False})
    assert not should_notify(order, cfg)
```

## 13. Dead Code and Duplication

**Delete dead code. Never comment it out.** Commented-out blocks, unused config fields, and superseded functions kept "for reference" all go. Git holds the history. A commented-out block is worse than no code: it looks maintained, every linter and test skips it, and it drifts silently until someone trusts it.

This is one of the most common AI failure modes. Asked to replace something, the tool leaves the original in place — commented out — and adds the replacement below it.

**Check before you write.** Before adding a helper, a client, a parser, or a config field, look for one that already exists. Reimplementing what is already there is the other common failure, because the tool cannot see what it did not read.

**Shared logic lives in one place.** When a second caller needs the same behavior, extract it rather than copying it. Where a family of classes shares a shape, the common work goes in the base class and subclasses declare only what differs.

## 14. What to Actively Avoid

| Anti-pattern                                    | Do this instead                                   |
| ----------------------------------------------- | ------------------------------------------------- |
| `os.environ` / `os.getenv`                      | Pydantic `BaseSettings` field                     |
| `TypedDict` for structured data                 | Pydantic `BaseModel`                              |
| `dict[str, Any]` as a function return type      | Named Pydantic model                              |
| Mutable module-level state                      | Constants, or a documented process-lifetime cache |
| Business logic in orchestration/I/O layers      | Logic in pure functions; adapters delegate to it  |
| Logic in `entrypoints/` or `app/`               | Move it to `core/`                                |
| A `core/` module importing a client or framework | Pass the data in; the call belongs in `infra/`    |
| Manual retry loops with `time.sleep`            | Framework retries or `tenacity`                   |
| Silent `except Exception: pass`                 | Named exceptions + logging (or document why)      |
| Bare `except:`                                  | Catch the exception you can actually handle       |
| `raise NewError(...)` discarding the cause      | `raise NewError(...) from err`                    |
| `assert` in production code                     | Raise a named exception                           |
| Exception names without an `Error` suffix       | `OrderNotFoundError`, inheriting a package base   |
| 500+ line modules                               | Split by responsibility                           |
| 100+ line functions                             | Small functions, single responsibility            |
| Moving data through your process to relocate it | Let the storage layer copy/move server-side       |
| `get_settings()` inside a lib or mid-execution  | Require config as a constructor parameter         |
| `config or get_settings()` fallback             | Required param, no default                        |
| Derived config models duplicating fields        | Accept the main settings class directly           |
| Constructor default restating a config default  | Config owns the default                           |
| Hardcoded env var strings in tests              | `config.model_copy(update={...})`                 |
| Relative imports                                | Absolute paths from the package root              |
| Imports inside functions to break a cycle       | Fix the module structure                          |
| `if TYPE_CHECKING:` to hide a bad dependency    | Fix the dependency arrow                          |
| `from typing import List, Dict, Tuple`          | Builtin generics: `list`, `dict`, `tuple`         |
| `Sequence`/`Callable` imported from `typing`     | Import from `collections.abc`                     |
| `Optional[X]` / `Union[X, Y]`                    | `X \| None` / `X \| Y`                              |
| Implicit optional (`x: str = None`)             | `x: str \| None = None`                            |
| Bare `Any`                                      | A real type, `object`, or `Any` plus a reason     |
| Bare `# type: ignore`                           | `# type: ignore[code]` plus a reason              |
| Type names inside variable names                | `orders_by_id`, not `order_dict`                  |
| f-strings in logging calls                      | `logger.info("count %s", n)`                      |
| `print()` for diagnostics                       | Module logger                                     |
| Blocking I/O inside `async def`                 | Async client or `asyncio.to_thread`               |
| Unbounded `asyncio.gather` over caller input    | Semaphore or batch size from config               |
| `Args:` / `Returns:` docstring blocks           | Prose that says what the signature can't          |
| Module-level docstrings on every file           | Only when purpose isn't clear from name           |
| Verbose docstrings restating the signature      | Brief one-liner, or prose for complex logic       |
| Commented-out code kept "for reference"         | Delete it; git has the history                    |
| Reimplementing a helper that already exists     | Search first, then extend what is there           |
| The same logic copy-pasted across two callers   | Extract it once                                   |

## Enforced Mechanically

These are checked by the files alongside this one — `ruff-base.toml` and `docstring_length.py` — plus `mypy`. They are not restated above; the config is the source of truth.

A repo picks up the baseline by extending it rather than copying it:

```toml
# pyproject.toml
[tool.ruff]
extend = "../agent-dev-harness/python-styleguide/ruff-base.toml"

[tool.ruff.lint.isort]
known-first-party = ["shared", "content_search"]   # per repo
```

**Excluded paths** — `.local/**` via top-level `exclude` (no lint, no format); `scripts/**` via `[lint].exclude` (no lint, still formatted). The docstring checks skip both as well.

**Formatting** — `ruff format`: line length, quote style, trailing commas, blank lines, whitespace, indentation. Never argue with the formatter.

**Prose length** — `W505` with `max-doc-length = 88` covers docstrings and comments, which the formatter never touches. `E501` stays off: with a formatter owning code lines it only fires on things the formatter deliberately left long, so `W505` is the precise instrument.

**Ruff rule families:**
- `E`, `W`, `F` — pycodestyle and pyflakes
- `I` — import grouping and ordering, with `known-first-party` set per repo
- `TID252` — relative imports banned
- `TC` — typing-only imports moved into `TYPE_CHECKING`
- `N` — naming case conventions
- `ANN` — missing annotations
- `UP` — modern syntax: `UP006` builtin generics over `typing.List`, `UP035` `collections.abc` over deprecated `typing` imports, `UP007`/`UP045` `X | Y` over `Union`/`Optional`. All autofixable.
- `B` — bugbear, including mutable default arguments
- `S` — bandit, including `assert` in non-test code
- `G`, `LOG` — logging call format
- `C4`, `SIM`, `RET`, `ARG`, `PIE` — comprehensions, simplifications, dead arguments
- `PL`, `C901` — argument count, statement count, branch count, complexity
- `PT` — pytest style
- `ASYNC` — blocking calls in async context
- `A` — builtin shadowing

**mypy** in strict mode: `disallow_untyped_defs`, `no_implicit_optional`, `warn_return_any`, `warn_unused_ignores`.

**Docstring volume** — `DOC001` (hard cap), `DOC002` (soft cap), and `DOC003` (docstring longer than its function body), all in `docstring_length.py`. No linter ships this: ruff's `D` rules check docstring *structure*, and pylint's `docstring-min-length` is the inverse. It has to be a custom AST check.

### Deliberately not linted

Four structural rules stay written rules, checked by review rather than by a tool:

1. **Import direction between layers** (§8) — would need `import-linter` as an extra dependency and a contract file per repo
2. **`get_settings()` called below an entry point** (§4) — expressible in ruff via `banned-api`, but only with per-repo module paths, so it cannot live in a shared baseline
3. **The `config or get_settings()` fallback** (§4) — no tool expresses it; it needs a custom AST check
4. **Derived config models duplicating settings fields** (§4) — needs field-by-field comparison across two models

These are the four most architectural rules in this document, and they are the four with no automatic enforcement. That is worth knowing when reviewing: everything else here either fails a check or is a judgment call, but these four are hard rules that will pass a clean build. Read for them explicitly.

A repo that wants rule 2 enforced locally can add it without any new tooling:

```toml
[lint.flake8-tidy-imports.banned-api]
"app.config.get_settings".msg = "entry points only; take config as a parameter"

[lint.per-file-ignores]
"entrypoints/**" = ["TID251"]
```
